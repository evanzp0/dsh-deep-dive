# 让插件像乐高一样装卸

## 0. 这篇论文到底想解决什么问题？
你写过带插件的系统吧？比如一个 Node.js 服务，运行中想：
- 装一个新插件（加载一段代码）
- 卸一个插件（把它的代码和影响清掉）
- 换一个插件的版本（热更新）

现实中的做法是啥？重启进程。 VSCode 禁用一个扩展都要重启窗口。为什么？因为插件运行时干了太多事：
```javascript
// 某个插件运行起来后做了这些事：
app.use('/api', routes);        // 注册了路由
db.connect();                    // 开了数据库连接
setInterval(sync, 1000);         // 起了定时器
emitter.on('msg', handler);      // 挂了事件监听
globalCache.set('foo', bar);     // 写了共享状态
```
现在要把这个插件卸载。问题来了：定时器关了吗？事件解绑了吗？连接断了吗？路由删了吗？
插件作者如果忘了写清理代码，这些东西就泄漏了——进程越跑越慢。

这就是论文说的 **时间维（temporal）** 问题：插件离场时，它对环境做过的所有修改，能不能被干净地全部撤销？

还有第二个问题。插件之间会互相依赖：
```javascript
// 插件 B 依赖插件 A 提供的"数据库服务"
const db = ctx.get('database');  // A 不在，这一行就崩
```
如果 A 还没加载、或者中途挂了、或者被卸载了，B 该怎么办？手动写一堆 `if (!db) { ... }` 和事件回调？
这就是论文说的**空间维（spatial）**问题：依赖能不能被声明出来，由系统自动接线、依赖变化时自动调整？

论文的全部野心就一句话：**让"装插件、卸插件、换插件"像插拔 U 盘一样安全，不用重启，也不会留下垃圾。** 而且它不是拍脑袋说"我行"，而是给出了数学证明。

## 1. 时间维：Reversible Effect (可逆副作用) —— "每做一次改动，就交出一张撤销小票"

### 1.1 核心思想（一个比喻）
想象你是一家店铺的收银员，店规只有一条：
**每收一笔钱，必须立刻开一张"退款单"；每张退款单都钉在一个板子上，按开单顺序排好。**

- 插件做的每个改动操作（注册路由、开连接、起定时器） = 收一笔钱
- 配套交出的撤销操作（注销路由、断连接、清定时器） = 退款单
- 系统把退款单按顺序钉在板子上 = track（追踪）
- 卸载插件 = 把板子上的退款单从后往前逐张执行 = recover（恢复）

卸载因此变得机械而可靠：不需要插件作者"记得清理"，因为清理代码和动作代码必须成对交上来，少交系统就不让你做这个动作。

### 1.2 论文的核心公式

#### 1.2.1 第一个公式：什么是 effect（副作用）

$$
f : \Gamma \to \Gamma
$$

*   $\Gamma$（Gamma）：环境 / 上下文 —— 就是系统当前的全部共享状态（注册了哪些路由、开着哪些连接、有哪些变量）。你可以把它想成一个巨大的 JS 对象。
*   $\to$：函数箭头，左边是输入类型，右边是输出类型。
*   $f$：一个改动操作（非幂等函数/副作用）。

我们可以用 TS 这样定义它：

```typescript
// Γ (Gamma) 就是系统当前的全部共享状态
type Gamma = {
  routes: string[];   // 注册的路由
  timers: Set<any>;   // 存活的定时器
};
```
整句人话：一个 effect（副作用）就是一个函数(f)，它接收旧环境 `Gamma`，返回新环境 `Gamma`。

#### 1.2.2 第二个公式：副作用 + 撤销副作用的操作 = "工单"

$$
(f, g)
$$

单独的 $f$ 只是改动，单独的 $g$ 只是撤销。只有把它们打包成一个二元组，才构成一个完整的、可逆的副作用，可以称之为"工单"。

在 TS 中，我们把它定义为 `ReversibleEffect`：

```typescript
// ==========================================
// 定义 (f, g)：“可逆副作用（工单）”的类型
// ==========================================
type ReversibleEffect = {
  forward: (env: Gamma) => Gamma;   // 正向改动 (f)
  backward: (env: Gamma) => Gamma;  // 撤销小票 (g，f 的左逆)
};
```
它向系统承诺："我不仅要改变世界（`forward`），还保证能把我改变的世界完美还原（`backward`）。"

注意：论文只要求 $g$ 是 $f$ 的**左逆**：$g \circ f = \mathrm{id}$。
$\circ$ 是函数复合，$(g \circ f)(x)$ 就是 TS 里的 `g(f(x))`，$\mathrm{id}$ 是"什么都不做的函数"（`x => x`）。

让我们看看 $\circ$（函数复合）在 TypeScript 中是如何表示的：

```typescript
// ==========================================
// 1. 普通的函数复合（操作的是“裸函数”）
// ==========================================
function compose(
  f: (x: Gamma) => Gamma, 
  g: (x: Gamma) => Gamma
): (x: Gamma) => Gamma {
  // 返回一个新的函数，而不是直接执行
  return (x) => g(f(x));
}

// g 是 f 的左逆：g ∘ f = id
// 在 TS 中表现为：compose(f, g)(env) === g(f(env)) === env
// 含义：g 撤销了 f，环境回到原样
```

为什么不要求反过来 $f(g(x)) = x$（右逆）也成立？因为现实里很多操作撤销后回不到字面意义上的原样——比如 `malloc` 了一块内存再 `free`，内存是还了，但 OS 整体内存布局不是原来那个样子。论文很务实：只要你撤销之后，站在"使用者"的角度看一切照旧，就算合格。

到这里，我们可以完整解释什么是 "副作用" 和 "可逆副作用"了:
- effect（副作用）: 是一个状态转换器（函数）。它输入当前的系统环境（Γ），经过一顿操作，输出一个被改变后的新环境（Γ）。
- reversible effect: 是一对函数(一份契约/工单)，它把“正向动作(f)”和“撤销动作(g)”死死绑定在一起。
  系统不接受单独的 f，你必须把 f 和 g打包交上来，系统才允许你执行。

#### 1.2.3 第三个公式：pair 的复合 —— 把"两步小的可逆副作用"打包成"一个大的可逆副作用"

$$
(f_1, g_1) \circ (f_2, g_2) := (f_1 \circ f_2, g_2 \circ g_1)
$$

这个公式规定了如何把两个小工单揉成一个大工单。注意撤销部分的顺序是反过来的（为了保证后进先出 LIFO）。

这里的 $ \circ $ 是定义在**二元组**上的复合操作。`compose` 不能直接套用到二元组上，因为 `compose` 只能处理“裸函数”，而这里操作的是包含两个函数的“工单对象”。我们用一个 TS 高阶函数 `composePair` 来模拟它：

```typescript
// ==========================================
// 2. 二元组的复合（操作的是“工单”）
// ==========================================
function composePair(plan1: ReversibleEffect, plan2: ReversibleEffect): ReversibleEffect {
  // 正向部分：数学上是 f1 ∘ f2
  // 套用普通 compose：先执行 plan2.forward，再执行 plan1.forward
  const newForward = compose(plan2.forward, plan1.forward);

  // 逆向部分：数学上是 g2 ∘ g1（注意：为了保证 LIFO，这里顺序反过来了！）
  // 套用普通 compose：先执行 plan1.backward，再执行 plan2.backward
  const newBackward = compose(plan1.backward, plan2.backward);

  // 返回一个全新的二元组（大可逆副作用）
  return { forward: newForward, backward: newBackward };
}
```

**总结**：公式本身只是在定义打包规则。而"后进先出（LIFO）"的撤销效果，是这套打包规则在被 JS 引擎从内向外求值时，自然产生的数学必然结果。

以下是按照附件中 TypeScript 类型定义和代码风格，为您改写后的 **1.2.4 节**完整内容：

### 1.2.4 第四个公式：effect context —— 自带“时光倒流”能力的超级上下文

$$
\partial\Gamma := \Gamma \times (\Gamma \to \Gamma)
$$

`∂Γ` 就是框架传递给插件的 `ctx` 的真实类型！普通的 Context 只关心“现在上下文是什么样”，而 Effect Context 是一个带可逆副作用的上下文。

**（1）让人晕车的地方：这三个 $\Gamma$ 到底啥关系？**

数学公式为了简洁，用了同一个符号 $\Gamma$ 来表示"环境"，但它**省略了时间维度**。实际上，这三个 $\Gamma$ 代表的是**同一个环境在时间线上的三个不同瞬间**。我们把 $\Gamma$ 想象成 **"一个房间的状态"**：

1. **第一个 $\Gamma$（乘号左边）："当前"的房间状态**
   * **含义**：插件做完一系列改动操作后，系统**此时此刻**的真实环境。
   * **比喻**：你走进房间，看到桌上多了一个杯子（这是插件留下的痕迹）。
2. **第二个 $\Gamma$（箭头 $\to$ 的左边）：撤销操作接收的输入**
   * **含义**：当你决定卸载插件时，你把这个"当前被污染的房间"交给了撤销操作。
   * **比喻**：清洁工（撤销操作）进门时，看到的正是那个"桌上有个杯子"的房间（接手烂摊子）。
3. **第三个 $\Gamma$（箭头 $\to$ 的右边）：撤销操作产出的输出**
   * **含义**：撤销操作执行完毕后，归还给系统的那个"干净、恢复原样"的环境。
   * **比喻**：清洁工干完活离开后，房间恢复了"桌上没有杯子"的初始状态（干净的过去）。

**人话总结：**
effect context 就是一个包含两个属性的对象（存档槽），记作 $(\gamma, \varphi)$：
* $\gamma$ (`gamma`)：**当前环境状态**。
* $\varphi$ (`phi`，读作 phi)：**撤销累积器**。它的初值是"什么都不做"（$\mathrm{id}$，即 `env => env`）。因为在你还没做任何改动时，如果要求你"撤销"，那当然就是"保持原样，什么都不用干"。

需要注意的是：
> 在原论文的完整语境中，**$\partial\Gamma$ 并不是指这个笛卡尔积里的“所有”组合，而是指其中“满足特定不变量（Invariant）”的合法组合的集合。** 换句话说，$\partial\Gamma$ 是 $\Gamma \times (\Gamma \to \Gamma)$ 的一个**子集**。
只有当 $\varphi$ 确实是 $\gamma$ 的合法撤销链时，$(\gamma, \varphi)$ 才属于 $\partial\Gamma$。

**（2）Effect Context ($\partial\Gamma$) 的作用是什么？**

普通的 Context（上下文）只关心“现在是什么样”。而 **Effect Context（$\partial\Gamma$）** 是一个被论文重新发明的、**自带“时光倒流”能力的超级上下文**，更准确地说，$\partial\Gamma$ 是“带有【撤销副作用能力】的上下文”。

一个生动的比喻：普通账本 vs Effect Context:
* **普通的 Context** 就像一本**银行总帐账本**，它只反映一个时点的账户余额，而不反映一个时期的账户流水变化。
  * 你存了 100 块，账本上写着“余额 100”。
  * 你又存了 50 块，账本上写着“余额 150”。
  * *问题*：如果现在系统要“回滚”到最初状态，账本只告诉你现在是 150，它**没有记录**你之前具体做了什么操作，你无法自动退回到 0。
* **Effect Context ($\partial\Gamma$)** 就像一本**银行总账账本 + 一叠按顺序钉好的“退款单”凭证**。
  * $\gamma$（当前状态）：账本显示“余额 150”。
  * $\varphi$（撤销累积器）：钉在最上面的是“退还 50 块的指令”，下面压着的是“退还 100 块的指令”。
  * *优势*：当系统调用 `recover` 时，它不需要猜，只需要从上往下撕退款单（执行 $\varphi$），就能**精确、机械地**把余额一步步退回到 0。

论文发明 $\partial\Gamma$ (effect context) 的根本目的，是为了**把“副作用”从一种“不可控的破坏”，变成一种“可追踪、可逆转的契约”**。从此，**“卸载插件能卸干净”不再是靠程序员的良心和记忆力，而是变成了系统底层数据结构（$\partial\Gamma$）的数学保证。**

**（3）用 TypeScript 代码"翻译"这个公式：**

```typescript
// Γ (Gamma) 就是系统当前的全部共享状态
type Gamma = {
  routes: string[];   // 注册的路由
  timers: Set<any>;   // 存活的定时器
};

// ∂Γ (Effect Context) 的类型定义：
// 这就是框架传递给插件的超级上下文 ctx 的真实类型！
type EffectContext = {
  gamma: Gamma;                     // 第一个 Γ：当前的环境状态
  phi: (env: Gamma) => Gamma;       // (第二个 Γ) => (第三个 Γ)：撤销操作
};

// 实际运行时的样子：
const context: EffectContext = {
  gamma: { routes: ['/a'], timers: new Set([123]) }, // 1. 当前状态（被插件修改过）
  phi: (currentEnv) => {                             // 2. 接收当前状态作为输入
    // ... 执行清理逻辑，比如删除 '/a'，清除定时器 123
    return cleanedEnv;                               // 3. 返回恢复干净后的状态
  }
};
```

**（4）"累积器"是什么？（见证套娃魔法）**

因为每做一个新动作，$\varphi$ (`phi`) 就会像俄罗斯套娃一样，把**旧的累积器包在外面，新的撤销操作放在里面**。在 JS 中，函数求值是从内到外的。这意味着**放在最内层的新撤销操作，会最先被执行**，完美实现了"后做的先撤"（LIFO）。

```typescript
// 用 TS 演示 effect context 的"撤销链"演变过程：

// 1. 初始状态：插件还没开始做任何事
let ctx: EffectContext = {
  gamma: { routes: [], timers: new Set() },
  phi: (env) => env // φ₀：撤销累积器，初值是"什么都不做"
};

// ==========================================
// 2. 插件执行第一个改动操作：注册路由 '/a'
// ==========================================
const undoA = (env: Gamma): Gamma => {
  return { ...env, routes: env.routes.filter(r => r !== '/a') };
};
// 【关键】数学公式：φ₁ = φ₀ ∘ undoA
// 旧的 phi 作为外层函数，包裹着新的 undoA（内层函数）。
// 为了在闭包中正确引用，我们先缓存旧的 phi (这正是 track 函数内部的核心机制)
const prevPhi1 = ctx.phi; 
ctx = {
  gamma: { ...ctx.gamma, routes: ['/a'] },
  phi: (env) => prevPhi1(undoA(env)) 
};

// ==========================================
// 3. 插件执行第二个改动操作：注册路由 '/b'
// ==========================================
const undoB = (env: Gamma): Gamma => {
  return { ...env, routes: env.routes.filter(r => r !== '/b') };
};
// 【关键】数学公式：φ₂ = φ₁ ∘ undoB
// 同样，新的 undoB 放在最内层（最先执行），旧的 phi_1 放在外层（后执行）
const prevPhi2 = ctx.phi;
ctx = {
  gamma: { ...ctx.gamma, routes: [...ctx.gamma.routes, '/b'] },
  phi: (env) => prevPhi2(undoB(env))
};


// 💡 见证奇迹的时刻：把 ctx.phi 彻底展开，你会看到这个完美的嵌套结构：
// ctx.phi(ctx.gamma) === prevPhi1( undoA( undoB(ctx.gamma) ) ) 
// 最终返回彻底干净的环境 { routes: [], timers: Set(0) }
// 
// JS 的函数求值顺序是"从内到外"（也就是数学复合的从右到左）：
// 
// 第 1 步：先执行最内层的 undoB(gamma)  -> 撤销 '/b' (后做的，最先撤！✅)
// 第 2 步：再执行中间层的 undoA(gamma)  -> 撤销 '/a' (先做的，后撤！✅)
// 第 3 步：最后执行最外层的初始 phi(gamma) -> 初始的"什么都不做"，返回彻底干净的环境
```

#### 1.2.5 第五个公式：track —— 做改动的同时，把撤销小票钉上去

$$
\mathrm{track}_\Gamma(f, g) = (\gamma, \varphi) \mapsto (f(\gamma), \varphi \circ g)
$$

`track` 本质上就是一个 "记账员"函数。我们直接用核心代码来实现它：

```typescript
// ==========================================
// 定义“记账员”：track 函数 (消费 ReversibleEffect)
// ==========================================
function track(effect: ReversibleEffect, ctx: EffectContext): EffectContext {
  return {
    // 1. 拆开工单，执行正向改动，更新环境
    gamma: effect.forward(ctx.gamma),
    // 2. 把新的小票塞进撤销链 (LIFO 后进先出)
    phi: (env) => ctx.phi(effect.backward(env))
  };
}
```
**奇迹就发生在第 2 步的闭包里**：`phi: (env) => ctx.phi(effect.backward(env))`。
旧的 `ctx.phi` 包裹在外层，新的 `effect.backward` 放在最内层。当未来系统调用这个新的 `phi` 时，JS 引擎会从内向外求值——**最先执行最内层的新撤销操作，完美实现了"后做的改动，最先被撤销"（LIFO）。**

#### 1.2.6 第六个公式：recover —— 一键回滚，清空案发现场

$$
\mathrm{recover}_\Gamma = (\gamma, \varphi) \mapsto (\varphi(\gamma), \mathrm{id}_\Gamma)
$$

如果说 `track` 是记账员，`recover` 就是终极的 "清场指令"。

```typescript
function recover(ctx: EffectContext): EffectContext {
  return {
    // 1. 砸下累积器：把当前环境喂给撤销链，层层剥开回到起点
    gamma: ctx.phi(ctx.gamma),
    // 2. 清空累积器：恢复成恒等函数 (id)，即"什么都不做"
    phi: (env) => env 
  };
}
```

### 1.3 用 TS 写一个迷你版（完整生命周期示例）

下面这段代码将上述所有概念串联起来，完美复刻了论文 §3.1 的核心机制：

```typescript
/**
 * 迷你可逆 effect 系统 —— 论文 §3.1
 * 核心不变量：每个改动操作，都必须交出配套的撤销操作
 */

type Gamma = {
  routes: string[];
  timers: Set<ReturnType<typeof setInterval>>;
};

type EffectContext = {
  gamma: Gamma;
  phi: (env: Gamma) => Gamma;
};

type ReversibleEffect = {
  forward: (env: Gamma) => Gamma;
  backward: (env: Gamma) => Gamma;
};

function track(effect: ReversibleEffect, ctx: EffectContext): EffectContext {
  return {
    gamma: effect.forward(ctx.gamma),
    phi: (env) => ctx.phi(effect.backward(env))
  };
}

function recover(ctx: EffectContext): EffectContext {
  return {
    gamma: ctx.phi(ctx.gamma),
    phi: (env) => env
  };
}

// ═══ 使用示例：模拟一个"插件"的生命周期 ═══════════

// 1. 初始化超级上下文
let ctx: EffectContext = {
  gamma: { routes: [], timers: new Set() },
  phi: (env) => env // 初始的“什么都不做”
};

// 2. 插件的第一个改动操作：注册路由 /a
ctx = track({
  forward: (env) => ({ ...env, routes: [...env.routes, '/a'] }),
  backward: (env) => ({ ...env, routes: env.routes.filter(r => r !== '/a') })
}, ctx);

// 3. 插件的第二个改动操作：起一个定时器
// 【关键】使用块级作用域 + 闭包，精确追踪"我自己"创建的那个定时器
// 这样撤销时只会清除自己的定时器，不会误杀其他插件的
{
  let myTimer: ReturnType<typeof setInterval>;
  
  ctx = track({
    forward: (env) => {
      myTimer = setInterval(() => {}, 1000);
      const newTimers = new Set(env.timers);
      newTimers.add(myTimer);
      return { ...env, timers: newTimers };
    },
    backward: (env) => {                        
      clearInterval(myTimer);          // ✅ 只清除我自己的定时器
      const newTimers = new Set(env.timers);
      newTimers.delete(myTimer);       // ✅ 只从全局集合中移除我自己的引用
      return { ...env, timers: newTimers };
    }
  }, ctx);
}

console.log(ctx.gamma.routes);      // ['/a']，环境被改了
console.log(ctx.gamma.timers.size); // 1，定时器在跑

// ── 卸载插件：一键回滚 ──────────────────────────────
ctx = recover(ctx);

console.log(ctx.gamma.routes);      // []  路由没了
console.log(ctx.gamma.timers.size); // 0   定时器关了
// 环境精确回到插件加载之前的样子 ✔
```
注意代码里最关键的设计：`track` 强制你传入一个包含 `forward` 和 `backward` 的工单。你想注册路由？先把"注销路由"的逻辑交出来。这就是论文把"清理"从"作者自觉"变成"系统强制"的方式。

### 1.4 真实的并发问题：多个插件同时在场怎么办？

上面只处理了一个插件"自己撤自己"。现实更复杂：插件 B 的改动可能插在插件 A 的两个改动之间。A 卸载时，它的撤销操作跑在一个"被 B 动过"的环境（`Gamma`）上——还能撤干净吗？

论文的答案是：**如果 A 和 B 的改动互相独立（可交换），就能。**

独立的形式化定义（Def.19）要求 A 和 B 必须满足两个条件：
1. **跨插件的两两操作满足交换律**：A 的每一个操作函数和 B 的每一个操作函数，无论谁先执行，最终呈现的 `Gamma` 物理状态都一样。
2. **一方的改动不会“扰动”另一方的撤销操作（不误伤队友）**：A 的撤销代码在 B 已经存在的环境下执行时，必须只清理 A 自己的垃圾。

**直觉例子：**
- ✅ **独立**：A 注册路由 `/a`，B 注册路由 `/b`。在 `Gamma.routes` 数组中，它们互不干扰。A 撤销时通过 `filter(r => r !== '/a')` 精确移除自己，无论 B 怎么加路由，A 都不会误删 B 的 `/b`。
- ❌ **不独立（会扰动）**：A 和 B 都往 `Gamma` 的同一个共享数组里 `push` 数据。A 的撤销操作写成了粗暴的 `pop()`（无脑弹出最后一个元素）。当 A 卸载执行 `pop()` 时，如果 B 已经执行了 `push`，A 就会把 B 的数据给弹出来！这就叫 A 扰动了 B 的 `Gamma` 状态。

**推论 Cor.21**：一组两两独立的插件，卸载顺序随便排，环境都能精确还原。这就是"并发装卸是安全的"的数学与代码层面的双重依据。
